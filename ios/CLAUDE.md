# Slate Pro iOS app

SwiftUI app for creators (photographers, videographers) to get booked with a contract in every booking. Spec: `../SPEC.md`. Setup and backend notes: `README.md`.

## Commands

- `xcodegen generate` regenerates `Slate.xcodeproj` from `project.yml`. Never edit the `.xcodeproj` and never commit it. Add new Swift files by dropping them in `Slate/` or `SlateTests/`; XcodeGen picks them up.
- Test: `xcodebuild test -project Slate.xcodeproj -scheme Slate -destination 'platform=iOS Simulator,name=iPhone 16' CODE_SIGNING_ALLOWED=NO`
- CI (`.github/workflows/ios.yml`) does the same on macOS. If you can't run Xcode (for example on Linux), CI is the compile check.

## Design rules (from the product owner; they apply to every screen)

- Swift and SwiftUI, iOS/iPadOS first, following Apple's HIG. Min iOS 17. Gate newer APIs with `#available`, and wrap iOS 18+ API in `#if compiler(>=6.0)`.
- Use system fonts via semantic text styles (never fixed sizes) and SF Symbols, so Dynamic Type works. Colors, spacing, radii, type, buttons and card styles come from `DesignSystem/DesignSystem.swift`. Don't hardcode literals.
- The look is the product owner's reference ("Creator Connect Pro"): dark first, a near-black page (`slateBackground`), deep violet-black cards with a thin violet-grey border (`card()`, `slateCard`, `slateHairline`), one violet accent (the `AccentColor` asset), rounded rectangles for buttons (`.slatePrimary` filled, `.slateOutline` outlined) and capsules for chips, with a violet glow on first-run screens (`slateGlowBackground()`). It is dark by default; Settings ▸ Look switches to Light or the system (`AppearancePreference`), so every color token has a Light value too. Words in the accent use `slateAccentText`, not `accentColor`. Lists and forms get `slateCard` rows and the page background (`.listRowBackground(Color.slateCard)`, `.scrollContentBackground(.hidden)` with `.slatePageBackground()`), so system gray never shows.
- Native patterns: `NavigationStack` per tab, `TabView` (Home, Bookings, Services, Messages, Profile), sheets with detents, swipe actions, `.refreshable`, context menus. Don't paint custom bar backgrounds; let the system draw bars.
- Generous whitespace, rounded continuous corners, subtle materials, spring animations (`Animation.slateSpring` etc.), haptics via `.sensoryFeedback` on key actions. Respect Reduce Motion (`motionSafe`).
- Accessibility first: VoiceOver labels on icon-only controls, 44pt minimum tap targets (`Metrics.minTapTarget`), contrast, and decorative images hidden from VoiceOver.
- Booking a service takes 3 taps or fewer (defined precisely in SPEC.md).

## Architecture

- `AppModel` (`@Observable`, `@MainActor`) is the single source of account state. Views read it from the environment.
- All server access goes through the `SlateBackend` protocol. `LocalBackend` (on-device, default, used by tests) and `SupabaseBackend` implement it. New features add methods to the protocol and both implementations; keep the local one working so the app runs with no setup.
- Pure logic (rules, validation, completeness) lives in `Core/` with no UI imports so it stays easy to test.
- Swift language mode is 5; don't enable strict concurrency or Swift 6 mode without a deliberate migration.

## Conventions

- **The product is called Slate Pro.** Everything a person reads (screens, permission messages, notifications, emails, share text, the PDF author, the name under the icon) says "Slate Pro", from `AppConfig.productName` where it is built in code. The working name "Slate" stays in code that nobody reads: the target and module (`import Slate`), folders, the `slate://` link scheme, bundle ids, storage keys and the placeholder domain `slate.example`. `scripts/check_product_name.py` fails CI when a string a person can read says a bare "Slate".
- Add unit tests for any logic you add in `Core/` or `ProfileDraft`. UI is verified by building and running, not unit tests.
- Keep `HandleRules` and the `creator_profiles.handle` SQL check in sync, and likewise the portfolio limit (12) in `AppConfig` and the SQL trigger.
- Booking rules live in two places that must agree: `AvailabilityEngine` + `PriceSummary` (Swift, used by the screen and `LocalBackend`) and `create_booking()` (SQL). Change one, change the other, and extend both test suites (`SchedulingBackendTests`, `supabase/tests/booking_rules.py`).
- Never take a price, duration or availability decision from the client. `BookingRequest` carries ids and a start time only; backends recompute the rest.
- Contract text is built in two places that must agree word for word: `ContractFormat` / `ContractContextBuilder` / `ContractRenderer` (Swift) and the `contract_*` functions in the contracts migration (SQL). `SlateTests/Fixtures/contract_golden.json` is checked by both test suites. Change the wording of a fixed text (cancellation policy, usage rights, formatting) in all three places. A change to what a signed contract says is a change to what people agreed to, so be deliberate.
- Names, notes and anything else a person types must go through `ContractFormat.sanitize` before it reaches a contract.
- The client signs the SHA-256 of the server-rendered text. Never compute that hash from anything the client supplied.
- Money is recorded only from Stripe's signed webhook (`payment_record_success`), never from the app. The only app-side way to mark a payment paid is `LocalBackend.completeSimulatedPayment`, which exists for on-device mode and which `SupabaseBackend` refuses. Never add another.
- Amounts are never taken from a request. `payment_prepare` works them out from the booking; the Edge Functions pass that on to Stripe.
- Refund rules live in `CancellationPolicy.refundPercent` / `RefundQuote` (Swift) and `refund_percent()` / `booking_refund_figures()` (SQL); `SlateTests/Fixtures/refund_golden.json` is checked by both. The 15-minute hold is `PaymentRules.holdMinutes` and `app_hold_minutes()`.
- Anything that can add to or revive a creator's active bookings must call `lock_creator_calendar()` first, before any row lock, so concurrent bookings queue instead of deadlocking on the exclusion constraint.
- Payment logic for the Edge Functions goes in `supabase/functions/_shared/payments.ts` (pure, dependency-injected) with tests in `supabase/function-tests`; keep `_shared/runtime.ts` and the `index.ts` files thin. Run `cd supabase/function-tests && npm ci && npm test && npm run typecheck`.
- A booking's conversation lines ("deposit paid", "cancelled") and its notifications are written by triggers on `bookings`, `payments` and `contracts`, not by the functions that change them, so no code path can forget to announce itself. The cancel, payment and contract triggers run at commit (`deferrable initially deferred`) so they see the finished picture, including refunds recorded after the cancel. `LocalBackend` mirrors each of them by hand (`appendSystemMessage`); keep the two in step and extend `booking_rules.py` and `MessagingBackendTests`.
- Delivery and reviews: the creator shares an `https` link (`share_delivery`), the client confirms receipt (`confirm_receipt`), and only then is the balance payable (`payment_prepare` and `LocalBackend.preparePayment` both require `receipt_confirmed_at`). A booking with nothing left to pay completes when the client confirms. A review is written only by `submit_review` (client of a completed booking, once); the `reviews` table is closed to the API and public pages use `list_reviews` / `creator_review_summary`. The link rule is `DeliveryRules.cleanLink` (Swift) and `delivery_url_clean()` (SQL, also a check constraint); reviewer names are `ReviewRules.displayName` and `review_display_name()`. `SlateTests/Fixtures/delivery_rules.json` is checked by both suites; change a rule in all three places. Never fetch a delivery link or put it in a notification or a system line, and always show the client its host before it opens.
- The delivery, receipt and review lines and notifications come from triggers like the others, but run per row (not deferred): they have nothing to wait for. `LocalBackend+Delivery.swift` mirrors them; keep it in step with `…_delivery_reviews.sql`.
- The push queue holds *facts*, not wording. `_shared/push.ts` words them (with `NoticeFormat` in Swift wording the same reminders for on-device mode); keep reminder wording and `ReminderPlanner` in step with `enqueue_due_reminders()`. Lead times, the message limit and message tidying are in `SlateTests/Fixtures/notification_rules.json`, checked by both suites.
- With a server (`backend.sendsPushFromServer`) the app schedules no local reminders; without one it schedules them all. Never both, or people get each reminder twice.
- Reminder syncs and conversation refreshes go through `CoalescedWork`, so an older run can't overwrite a newer one. Anything that changes `bookings` calls `bookingsChanged()`.
- `send-push` must only ever answer the service role key or `PUSH_CRON_SECRET` (`isAuthorized`); it is deployed with `--no-verify-jwt`, so that check is the only gate.
- Sizes and spacing: big decorative symbols use `.heroSymbol(_:)`, never `.font(.system(size:))`. Layout numbers (button label height, icon column, content widths, placeholder heights, tiles) are `Metrics` tokens; frames that hold text are `minWidth`/`minHeight`, not fixed. Two things side by side that can collide at large text use `AdaptiveStack` or `ViewThatFits` so they stack at accessibility sizes.
- Colors: text on the accent is `slateOnAccent`. `slateSuccess`/`slateWarning`/`slateDanger` are tuned for at least 4.5 : 1 as text, so use them for text, not just symbols; don't use the raw system green/orange/red for words. A signature (drawn or typed, on screen or on a contract) sits on `slatePaper` in `slateInk` in both appearances.
- VoiceOver: decorative images and chevrons are `.accessibilityHidden(true)`; an icon-only control has an `.accessibilityLabel`; a row that reads as one thing is `.accessibilityElement(children: .combine)`.
- The home screen widget never touches the network. `AppModel.bookingsChanged()` publishes a `WidgetSnapshot` (built by `WidgetSnapshotBuilder`) into the App Group through a `WidgetPublisher`; the widget only reads it. `Shared/` is compiled into the app *and* the widget extension, so nothing in it may refer to app types. The group id is `APP_GROUP_ID` in `Config/App.xcconfig`; the entitlements files and both Info.plists use it.
- Companies. A company is an owner like a person: its id is a profile id, and packages, contract templates, hours, the portfolio, the profile and the payment account are found by it. In the app, `AppModel.ownerID` is whose that is (the person's, or the company on screen); bookings, payments and messages always belong to the *person*, and `visibleBookings` sorts them by account. Never decide "is this booking mine?" with `booking.creatorID == userID`: use `Booking.isProviderFor`, `Booking.involves` or `AppModel.isProviderSide`, because a company's booking has the company as its `creatorID` and a person as `assignedTo`.
- Permissions are decided in the database. Every company write goes through `acts_for()` (owner-scoped data) or `provider_access()` (a booking), and `LocalBackend.permits` / `authorizeOwner` / `providerAccess` follow them rule for rule. A permission exists in three places that must agree: `OrgPermission` (Swift), `org_role_allows()` (SQL) and `SlateTests/Fixtures/team_permissions.json`, which `TeamCoreTests` and `supabase/tests/team_rules.py` both read. The app hides what a role cannot use (`AppModel.can(_:)`, `canManage(_:)`, `canAssign(_:)`), but hiding is a courtesy: never rely on it.
- Team booking rules live in two places that must agree: `TeamAvailability` / `AssignmentPlanner` (Swift) and `team_availability()` / `create_booking()` / the assignment functions (SQL). A person is never in two places: the exclusion constraint is on `assigned_to`, so personal and company bookings share one calendar. Extend `TeamBookingTests` and `supabase/tests/company_rules.py` with any change.
- Seat numbers (minimum, maximum), invite lifetime and the grace period are `app_settings` rows read through `team_config()` and `TeamConfig`. Never write them as literals; `TeamConfig.standard` is only the on-device default and the fallback.
- A company's contract names the company (`providerLegalName`) and is countersigned by the designated signer, who is fixed when the *client* signs (`countersignerID/Name/Title`), so changing the signer never alters a contract already made.
- Every error token a team function raises must be mapped in `SupabaseBackend.mapTeamToken` (`TeamRowDecodingTests` reads the migrations to check). `Fixtures/team_rows.json` is what the team functions really return: if you change one's output, run `PGPORT=5432 python3 supabase/tests/dump_team_rows.py` and commit the file; CI runs it with `--check`.
- Team harnesses, each against a throwaway Postgres: `team_rules.py` (organizations, roles, invites), `company_rules.py` (services, assignment, contracts, upgrade), `billing_rules.py` (seats and plans), plus the Node tests for billing in `supabase/function-tests`. On a device with no server `LocalBackend.completeSimulatedJoin` stands in for a teammate accepting an invite and `actAs` for being someone else; `SupabaseBackend` refuses both, and billing is unavailable.
- Featured creators (the explore grid under the search field on a client's Home) are ordered by `FeaturedRules` (Swift) and `featured_creators()` (SQL), which must agree: `SlateTests/Fixtures/featured_rules.json` is read by `FeaturedRulesTests` and `supabase/tests/featured_rules.py`, and its `rowColumns` list is the columns the Supabase row decoder (`SupabaseBackend.FeaturedRow`) reads. With a client's place (`ClientPlace`, a city rounded to about a kilometre, kept on the phone per person and sent only as the `p_lat`/`p_lon` arguments of that call), creators who work there (distance from the client to their city within their travel radius, 40 km if none; `GeoRules.distanceKm` matches the haversine in the SQL) come first; the fixture's `clients` and `distances` are checked by both sides. Never store a client's place on a server or send it unrounded. It is worked out, never paid for or hand-picked: don't add a way to buy or force a position. On a device with no server, `LocalBackend(offersSampleCreators: true)` (only `BackendFactory` turns it on) makes eight sample creators the first time creators are asked for; tests and previews never do, so they start empty.
- Cards on file (Profile ▸ Payment methods). Stripe holds every card; nothing here may hold a number, and Stripe's reference to a card (`client_cards.stripe_payment_method_id`) never reaches the app: the app reads `client_cards` only by `SupabaseBackend.cardColumns` (column permission refuses the rest). A creator can charge a saved card only through `payment_prepare_saved` (which calls `payment_prepare`, so the amount is the booking's balance and it is payable only after the client confirms their files), only if the client allowed that creator (`card_grant`: a creator the client has booked, their own unexpired card, the current `card_consent_version()`), and only whoever `provider_access(…, 'manage')` allows. A permission can be stopped at any moment and goes with its card. Money is still recorded only by the webhook (`payment_record_success`; the saved-card charge marks its intent `metadata.saved_card`). The rules live in `…_cards_on_file.sql` and `CardRules` / `CardConsent`, and `SlateTests/Fixtures/card_rules.json` (limit, wording version, expiry cases) is checked by both; `Fixtures/card_rows.json` is what the functions really return (`card_rules.py --dump` rewrites it, and CI fails if the database stops matching it). Changing the agreement's wording is a new `consentVersion` in Swift and SQL. `LocalBackend+Cards.swift` mirrors it with pretend cards; keep the two in step and extend `card_rules.py`, `CardTests` and `function-tests/cards.test.ts`. Card Edge Function logic lives in `_shared/cards.ts` (pure, dependency-injected).
- Slate Files (photos and videos delivered in the app). The first delivery is by files *or* by link, never both: files can't follow a shared link or a paid balance (`files_first_delivery_locked` / `FileRules.firstDeliveryLocked`), and a revision needs a first delivery and nothing owed (`files_revision_allowed`). Who can open a preview or an original is decided by `files_can_open` (Swift: `FileRules.canOpen`) and enforced by the policies on the private `deliveries` bucket (`files_may_store` / `files_may_read`), evaluated when a link is made, so the app never decides it and a locked original can't be linked. Limits are the `files` row of `app_settings` (`files_config()`, `FilesConfig`); never write them as literals. The caps, allowance, 30 days, reminders, names and open matrix live in SQL and Swift and are checked against `SlateTests/Fixtures/file_rules.json`; `file_rows.json` is what the functions really return (`file_rules.py --dump` rewrites it). Delivering a first time marks the booking delivered *and received* (a hosted delivery has no confirm step; the receipt trigger fires only when a link exists), which is what makes the balance payable. Deleting rows doesn't free bytes: every path that stops being needed goes in `storage_purge` and the `expire-files` job deletes it (logic in `_shared/files.ts`, which only ever deletes paths that match `<owner>/<booking>/<file>/original|preview`). `LocalBackend+Files.swift` mirrors the SQL rule for rule with the bytes in the app's folder; keep the two in step and extend `file_rules.py`, `FileBackendTests`, `FileModelTests` and `function-tests/files.test.ts`. Storage paths are lowercase UUIDs.
- Run the SQL rule tests with a local Postgres: `PGPORT=5432 python3 supabase/tests/booking_rules.py` (needs `psycopg2`).
- Tests that depend on "now" must not depend on the time of day. Use fixed dates (see `TestClock`) or pick days a few days ahead.
- Storage paths use lowercase UUIDs, because Postgres compares `auth.uid()::text` case-sensitively.
- Secrets live in `Config/Secrets.xcconfig` (git-ignored). Only the Supabase anon key belongs in the app, never the service-role key.
